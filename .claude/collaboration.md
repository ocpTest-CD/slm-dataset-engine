# 协作规范

## 基本协作

- 修改前先检查 Git 状态和目录结构。
- 不覆盖用户已有改动；遇到未提交改动时先判断是否相关。
- 保持改动范围小，避免顺手重构无关模块。
- 先理解现有代码风格，再新增抽象。
- 引入新依赖前说明用途、替代方案和环境影响。
- 完成后说明修改了哪些文件、运行了哪些检查、还有哪些风险。

## Git 与提交

- 提交信息使用中文。
- 提交信息应描述变更目的，而不是只写“更新”。
- 推荐格式：

```text
初始化数据集工作台协作文档
新增数据导入任务状态机
修复样本审核分页异常
补充数据集导出质量报告
```

- 不使用破坏性 Git 命令，除非用户明确要求。
- 不提交大体积数据、模型权重、checkpoint、日志、缓存和密钥。

## 文件规模

- 每个研发文件尽量控制在 500 行以内。
- 单文件确有必要时最多不超过 700 行代码。
- 超过限制前应拆分：
  - 前端拆分页面、组件、hooks、api、schema、table columns。
  - Go 拆分 handler、service、repository、domain、jobs。
  - Python 拆分 parser、processor、schema、quality、exporter。
- 自动生成文件可以例外，但应放在明确目录并标注生成来源。

## 数据与安全

- 不在代码、配置、文档或日志中写入 API key、token、账号、私有服务地址。
- 样例数据必须脱敏且最小化。
- 日志优先记录统计摘要，不输出大量原始样本。
- 数据源需要记录授权边界和使用限制。
- AI 生成样本必须记录生成来源，不能和人工标注样本混淆。

## 研发节奏

- MVP 优先打通主流程：导入、处理、审核、导出。
- 不急于做复杂流程画布、插件市场或多租户系统。
- 新增功能时优先提供最小样例或 dry-run。
- 核心流程必须能回放，不能依赖命令历史或人工记忆。

## 文档与上下文

- 重要架构决策应更新 `.claude/architecture.md` 或项目 docs。
- 技术栈规范变化应更新 `.claude/technical-standards.md`。
- 协作规则变化应更新本文件和必要时更新 `../AGENTS.md`。
- `.claude/` 是按需阅读目录，新增上下文文件时必须在 `.claude/README.md` 登记。
